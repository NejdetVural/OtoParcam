# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OtoParcam is a web-based inventory and sales management system for businesses that sell **used auto spare parts**. Customers find compatible parts by vehicle brand/model; administrators manage products, inventory, and orders through a purchase-request workflow with optional phone-negotiated pricing. Full domain context lives in `docs/` — read `docs/01-Project-Vision.md` and `docs/02-Business-Requirements.md` before implementing business logic, since the numbered `BR-*` rules there are the source of truth for validation/behavior decisions. `docs/Notes/ DECISION_LOG.md` (note the leading space in the filename) records accepted architecture decisions with rationale — e.g. why there's no stock-quantity field (each used part is its own `Product`), why `Price` is nullable, why there's no generic `Condition` field (defects are free-text in `Description` instead), and why the DB engine is SQL Server rather than PostgreSQL.

Planned stack (per `docs/01-Project-Vision.md`): ASP.NET Core Web API + EF Core + SQL Server backend; React + TypeScript + Tailwind frontend; JWT auth via ASP.NET Core Identity, FluentValidation, Serilog, Docker.

Current state: the backend is feature-complete for v1.0 scope. It has a working Clean Architecture skeleton with domain entities, an EF Core `DbContext` with Fluent API configurations for every entity, an applied `InitialCreate` migration, ASP.NET Identity + JWT bearer authentication, and role-based authorization policies. All eleven feature slices are implemented end-to-end through Application → Infrastructure → API: **Auth** (register/login/confirm-email), **Categories**, **Vehicle Brands**, **Vehicle Models**, **Products** (including nested Product Images and Product Compatibility endpoints, plus internal-only `AcquisitionCost`/`AcquisitionSource` fields), **Favorites**, **Purchase Requests** (the core order workflow, including the admin negotiation endpoint at a separate `/admin/purchase-requests` base path), **Customer Profile** (`/users/me`), **Dashboard** (`/admin/dashboard` summary stats), **Reports** (`/admin/reports/statistics`, an on-demand PDF sales/inventory report, added 2026-08-10), and **Acquisition Batches** (`/admin/acquisition-batches`, added 2026-08-11 — see below). `frontend/` has a real Vite/React/TS scaffold under active build-out (see `docs/Notes/EntityProcess.md`/memory for what's wired so far) — it is not the empty placeholder its `README.md` alone would suggest; `database/` and `assets/` remain empty placeholders.

**Acquisition Batches** (added 2026-08-11, BR-72/73/74): parts are frequently bought together as one lump-sum purchase (e.g. an entire insurance-total-loss vehicle) but always sold individually. `AcquisitionBatch` (`Source`/`TotalCost`/`PurchaseDate`/`Notes`) captures that purchase once; `Product.AcquisitionBatchId` optionally links a product to one. `Product.AcquisitionCost`/`AcquisitionSource` keep their original meaning unchanged — a per-product override, still fully usable standalone with no batch involved — nothing about individual pricing/selling changed. `ProductDto` additionally exposes `EffectiveAcquisitionCost`/`EffectiveAcquisitionSource` (own override if set, else the batch's `TotalCost` split evenly across every product currently linked to it, recomputed on every read — never baked into a stored value) and `AcquisitionBatchId`/`AcquisitionBatchSource`; all four, like the raw fields, are stripped to `null` for non-Administrator callers. `ReportService`/`DashboardService` use the effective cost, and the statistics PDF has a new "Toplu Alımlar" (batches) section showing per-batch part/sold/available counts, revenue-so-far, and profit-so-far (revenue recouped vs. the lump sum paid — negative until enough parts sell to cover it). See DECISION-007 in ` DECISION_LOG.md` for the full rationale.

## Commands

Run from the repository root (`OtoParcam.sln` lives at the repo root, not under `backend/`):

```
dotnet build OtoParcam.sln                                   # build all projects
dotnet run --project backend/src/OtoParcam.API                # run the API
dotnet watch --project backend/src/OtoParcam.API              # run with hot reload
```

In development, the API serves Swagger UI at `/swagger` (JWT bearer auth is wired into the Swagger "Authorize" button — paste `Bearer {token}`).

**Secrets** (added 2026-08-11, after the repo was confirmed public on GitHub): `appsettings.json`/`appsettings.Development.json` are tracked in git and must never contain a real value for `Jwt:Secret` or any real DB credential — `appsettings.Development.json`'s `Jwt` section deliberately has no `Secret` key. Locally, the signing key comes from .NET User Secrets (`UserSecretsId` is set on `OtoParcam.API.csproj`); set one with `dotnet user-secrets set "Jwt:Secret" "<32+ random chars>" --project backend/src/OtoParcam.API` (already done on this machine — a fresh clone needs to run it once). In production, supply `Jwt:Secret` and `ConnectionStrings:DefaultConnection` via environment variables (`Jwt__Secret`, `ConnectionStrings__DefaultConnection`) or the hosting platform's secret manager — never a committed `appsettings.Production.json` (blocked by `.gitignore` as a reminder, but don't rely on that alone).

EF Core migrations (an `InitialCreate` migration already exists under `backend/src/OtoParcam.Infrastructure/Migrations/` — add new ones the same way when the model changes):

```
dotnet ef migrations add <Name> -p backend/src/OtoParcam.Infrastructure -s backend/src/OtoParcam.API
dotnet ef database update      -p backend/src/OtoParcam.Infrastructure -s backend/src/OtoParcam.API
```

`-p` (project) must be `Infrastructure` (it owns `ApplicationDbContext`); `-s` (startup project) must be `API` (it owns the connection string in `appsettings.Development.json` and the DI wiring). SQL Server LocalDB (`(localdb)\mssqllocaldb`) is the dev target — it ships with Visual Studio, no separate install needed; start it manually with `sqllocaldb start MSSQLLocalDB` if a command needs it running (it also auto-starts on first connection). The dev connection string points at database `OtoParcamDb`.

`backend/tests/OtoParcam.Infrastructure.Tests` (xUnit, added 2026-08-10) covers `ProductService`'s status-visibility rules (admin-vs-public filtering, Hide/Restore transitions, `SoldPrice` derivation from the approved `PurchaseRequestItem`) against EF Core's `InMemory` provider — a deliberate tradeoff for fast, zero-dependency unit tests of service logic, not a substitute for exercising real SQL Server behavior (constraints, cascade deletes) that the Fluent API configurations enforce. Run with `dotnet test backend/tests/OtoParcam.Infrastructure.Tests`, or `dotnet test OtoParcam.sln` for the whole solution. Follow its pattern (an in-memory `ApplicationDbContext` per test via `UseInMemoryDatabase(Guid.NewGuid().ToString())`, real service classes under test, no mocking) for new test projects.

`git` is not on PATH in this environment; if a shell `git` invocation fails with "not recognized", fall back to a bundled copy, e.g. `"C:\Program Files\Microsoft Visual Studio\2022\Community\Common7\IDE\CommonExtensions\Microsoft\TeamFoundation\Team Explorer\Git\cmd\git.exe"`.

**Frontend tests** (Vitest + React Testing Library, added 2026-08-12): configured via the `test` block in `frontend/vite.config.ts` (using `defineConfig` from `vitest/config` rather than `vite`, so the config stays one file) and `frontend/src/setupTests.ts` (imports `@testing-library/jest-dom/vitest` for the extra DOM matchers). Run with `npm run test` (`vitest run`) from `frontend/`. Tests live next to the code they cover as `*.test.ts`/`*.test.tsx` — so far: `lib/phone.test.ts`, `api/errors.test.ts`, `components/ui/NotificationBubble.test.tsx`. ## Architecture

Clean Architecture, 4 projects under `backend/src/`, all targeting net9.0:

- **OtoParcam.Domain** — entities, enums, `BaseEntity` (Id/CreatedAt/UpdatedAt), and `Constants/Roles.cs` (`Administrator`/`Customer` string constants used by both ASP.NET Identity role checks and `[Authorize(Roles = ...)]`/policy checks). No project references (innermost layer). Still contains a leftover placeholder `Class1.cs` — safe to delete when touching this project, it's unused.
- **OtoParcam.Application** — references Domain only. One folder per feature slice (`Auth/`, `Categories/`, `VehicleBrands/`, `VehicleModels/`, `Products/`, `Favorites/`, `PurchaseRequests/`, `Users/`, `Dashboard/`, `Reports/`, `AcquisitionBatches/`), each holding an `I<Feature>Service` interface plus a `<Feature>Models.cs` with request/response DTOs. All CRUD slices (Categories/VehicleBrands/VehicleModels/Products/Favorites/PurchaseRequests) follow the same established convention — copy it for any future slice:
  - An `<Entity>OperationStatus` enum (`Success`, `NotFound`, plus feature-specific failure cases like `InvalidCategory`, `Conflict`, `LimitExceeded`) rather than throwing exceptions for expected failure paths.
  - A `<Entity>Result`/`<Entity>DeleteResult` wrapper class with static factory methods (`Success(...)`, `NotFound()`, etc.) carrying the `Status`, an optional DTO payload, and an optional `Error` message.
  - Controllers `switch` on `result.Status` to map to HTTP status codes (`Success`→200/201/204, `NotFound`→404, validation failures→400, conflicts→409) — see `ProductsController.cs` for the fullest example (Success/NotFound/InvalidCategory/InvalidVehicleModel/InvalidPrice all mapped explicitly).
  - List endpoints take a `<Entity>ListQuery` bound via `[FromQuery]`; `Products` additionally returns a generic `PagedResult<T>` (`Items`/`Page`/`PageSize`/`TotalCount`/`TotalPages`).
- **OtoParcam.Infrastructure** — references Application + Domain, plus a `FrameworkReference` to `Microsoft.AspNetCore.App` (required because it's a plain class library, not `Sdk.Web`, so ASP.NET Identity/JWT types like `AddIdentity`/`AddJwtBearer` aren't available by default). Holds:
  - `Persistence/ApplicationDbContext.cs` — `IdentityDbContext<ApplicationUser, IdentityRole<Guid>, Guid>`, auto-stamps `CreatedAt`/`UpdatedAt` on every `BaseEntity` in an overridden `SaveChangesAsync`. `ApplicationUser` gets the same stamping via a second loop over `ChangeTracker.Entries<ApplicationUser>()` (fixed 2026-08-12 — it isn't a `BaseEntity` since it already extends `IdentityUser<Guid>`, so it was previously silently excluded from the `BaseEntity` loop and every account, including seed data, had `CreatedAt`/`UpdatedAt` stuck at `0001-01-01`; accounts registered before this fix keep that stale value on record, same pattern as `PrivacyPolicyAcceptedAt` in BR-80).
  - `Persistence/Configurations/*.cs` — one `IEntityTypeConfiguration<T>` per entity, applied via `ApplyConfigurationsFromAssembly`. This is where BR-driven schema rules live (column types/precision, FK delete behavior, unique/check constraints) — see `05-Database-Design.md` for the values each one is meant to match.
  - `Migrations/` — `InitialCreate` (generated 2026-07-24) plus the model snapshot. Regenerate/add migrations here whenever entities or configurations change.
  - `Identity/RoleSeeder.cs` — `SeedRolesAsync(IServiceProvider)`, idempotently creates the `Administrator`/`Customer` Identity roles; called once from `API/Program.cs` at startup inside a scoped `IServiceProvider`.
  - `Services/AuthService.cs` — implements `IAuthService`: `RegisterAsync` creates the Identity user, assigns the `Customer` role, and generates (but only logs, doesn't email) an email-confirmation token; `LoginAsync` accepts either email or phone number, rejects unconfirmed emails, and issues a JWT with the user's roles pulled via `UserManager.GetRolesAsync()` embedded as role claims (stateless bearer auth doesn't populate roles from the DB per request the way cookie-based Identity sign-in does); `ConfirmEmailAsync` decodes a base64url-encoded token and confirms via Identity. `RequestPasswordResetAsync`/`ResetPasswordAsync` (BR-81, added 2026-08-12) follow the same pattern as email confirmation — a base64url-encoded ASP.NET Identity token (`GeneratePasswordResetTokenAsync`/`ResetPasswordAsync`, no new DB column needed since the token is tied to the security stamp), only logged server-side rather than emailed; `RequestPasswordResetAsync` always succeeds from the caller's perspective (silently no-ops for an unknown email) to avoid account enumeration.
  - `Services/CategoryService.cs`, `VehicleBrandService.cs`, `VehicleModelService.cs`, `ProductService.cs` — implement the corresponding `Application` interfaces directly against `ApplicationDbContext` (no repository layer). Each validates FK references exist before insert/update (e.g. `ProductService` checks `CategoryId`/`SourceVehicleModelId` exist, `VehicleModelService` checks `VehicleBrandId` exists and `EndYear >= StartYear`) and blocks deletes that would orphan child rows (Category/VehicleBrand/VehicleModel all check for referencing rows before allowing delete, per BR-42/46/52). `ProductService` also owns the nested Product Images (`AddProductImageAsync`/`DeleteProductImageAsync` — auto-assigns/recompacts `DisplayOrder`, enforces the 1–10 image range), Product Compatibility (`AddProductCompatibilityAsync`/`RemoveProductCompatibilityAsync`/`GetProductCompatibilityAsync` — enforces the unique `(ProductId, VehicleModelId)` pair and validates the vehicle model exists), and `MarkProductSoldAsync` (admin-only direct "mark as sold" with a price, no purchase request involved — rejects an already-Sold product or a negative price; BR-78) methods, matching the entity's document 1:1.
  - `Services/FavoriteService.cs` — implements `IFavoriteService`: enforces the unique `(ApplicationUserId, ProductId)` pair (`Duplicate` status) and validates the product exists before adding.
  - `Services/PurchaseRequestService.cs` — implements `IPurchaseRequestService`: creates purchase requests only for products with `Status == Available` (BR-14), snapshotting `OriginalPrice` from `Product.Price` at creation time and never mutating it afterward (BR-31). The **customer** drives the terminal transitions themselves — confirm → `Approved`, reject → `Rejected` — while `cancel` is only valid while `Pending`; the **admin**-only negotiation endpoint (`UpdateNegotiationAsync`) sets `NegotiatedPrice` per item and moves status to `WaitingForCustomerConfirmation`, itself only valid while `Pending`/`WaitingForCustomerConfirmation` (see BR-26/BR-32 in `02-Business-Requirements.md` — the admin only negotiates pricing, the customer approves or rejects). Confirming to `Approved` flips `Product.Status` to `Sold` and stamps `Product.SoldPrice` from `NegotiatedPrice ?? OriginalPrice` (BR-36); `ProductService.MarkProductSoldAsync` is the other, purchase-request-free path to the same `Sold`/`SoldPrice` state (BR-78). Cancelling/rejecting never touch product state (BR-21). All customer-facing reads/writes are scoped to the caller's own requests, and a mismatch returns `NotFound` rather than `Forbidden` so existence isn't leaked (BR-15).
  - `Services/UserProfileService.cs` — implements `IUserProfileService`: reads/updates the caller's own `FirstName`/`LastName` directly against `ApplicationDbContext.Users` (no `UserManager`, since no security-sensitive fields are touched); Email/PhoneNumber are intentionally not editable here (out of v1.0 scope per the API spec).
  - `Services/DashboardService.cs` — implements `IDashboardService.GetDashboardStatsAsync`: returns total product count, total customers (counted via `AspNetUserRoles` membership in the `Customer` role, not total user rows — relevant since every registered account, including admins, also holds `Customer`), pending purchase request count, and "products awaiting attention" (an implementation choice, not spec-defined: `Available` products with zero images or zero compatibility rows — ties into the BR-02/BR-07 non-blocking gap noted below).
  - `Services/ReportService.cs` — implements `IReportService`: `GetStatisticsReportDataAsync(ReportPeriod period = AllTime, ...)` (the testable data-computation half — product counts by status, total customers, pending requests, per-Sold-product revenue/cost/profit read from `Product.SoldPrice` directly (covers both the purchase-request and admin-marked-sold paths identically) against the batch-aware effective acquisition cost, Available-inventory list/acquisition value, and a per-`AcquisitionBatch` rollup) and `GenerateStatisticsReportPdfAsync` (renders that data to PDF bytes via the QuestPDF package, Community license, set once in a static constructor, with a styled slate/blue/emerald-rose brand palette — colored header band, a profit hero banner, KPI stat tiles, zebra-striped tables). `period` (`AllTime`/`Daily`/`Weekly`/`Monthly`) scopes only the Sales Performance section to a rolling window ending now, via `Product.SoldAt` — every other section always reflects current state (BR-79). Kept as two separate interface methods specifically so the data computation can be unit-tested without invoking QuestPDF's layout engine.
  - `Services/AcquisitionBatchService.cs` — implements `IAcquisitionBatchService`: CRUD over `AcquisitionBatch`, plus a per-batch rollup (part/available/sold/hidden counts, estimated cost per part, revenue-so-far, profit-so-far) computed by loading every `Product` linked to the batch regardless of status. Blocks delete (`Conflict`) while any `Product` still references the batch, matching the Category/VehicleBrand/VehicleModel delete-blocking pattern.
  - `DependencyInjection.cs` — `AddInfrastructureServices(IServiceCollection, IConfiguration)` extension method: registers `ApplicationDbContext` (SQL Server), ASP.NET Identity, every `I<Feature>Service` → `<Feature>Service` mapping, JWT bearer authentication (reads the `Jwt` config section: `Secret`/`Issuer`/`Audience`/`ExpiryMinutes`), and the `Administrator`/`Customer` authorization policies. Called once from `API/Program.cs`.
- **OtoParcam.API** — references **both Application and Infrastructure**. `Program.cs` calls `AddInfrastructureServices`, configures Swagger/OpenAPI with a Bearer security scheme, runs `RoleSeeder.SeedRolesAsync` at startup, registers a fixed-window rate limiter (10 req/min per client IP, policy name `"auth"`, added 2026-08-11) applied to `AuthController` via `[EnableRateLimiting("auth")]` to slow down credential-stuffing against login/register, and wires `UseAuthentication()`/`UseAuthorization()` before `MapControllers()`. `Controllers/` holds `AuthController`, `CategoriesController`, `VehicleBrandsController`, `VehicleModelsController`, `ProductsController` (the last also owns the nested `/products/{id}/images` and `/products/{id}/compatibility` routes, plus the admin-only `PATCH /products/{id}/sell` direct-sale action), `FavoritesController` (`/favorites`, `[Authorize(Roles = Roles.Customer)]` at the controller level), `PurchaseRequestsController` (`/purchase-requests`, also `[Authorize(Roles = Roles.Customer)]`; owns `cancel`/`confirm`/`reject` as `PATCH .../cancel|confirm|reject`), `AdminPurchaseRequestsController` (a separate controller at `/admin/purchase-requests`, `[Authorize(Roles = Roles.Administrator)]`; owns the review-all list and `PATCH .../negotiation`), `UsersController` (`/users/me`, `[Authorize(Roles = Roles.Customer)]`), `DashboardController` (`/admin/dashboard`, `[Authorize(Roles = Roles.Administrator)]`), `ReportsController` (`/admin/reports/statistics`, `[Authorize(Roles = Roles.Administrator)]`, returns a `File(...)` result with `application/pdf` content type), and `AcquisitionBatchesController` (`/admin/acquisition-batches`, `[Authorize(Roles = Roles.Administrator)]` at the controller level, like Dashboard/Reports — every action is admin-only, not just writes, since cost data must never leak) — all list/detail `GET`s on public resources are public (`[AllowAnonymous]` implicitly, no attribute needed), all other actions carry role-based `[Authorize]`. All customer/admin-scoped controllers that need the caller's identity pull it from the JWT `sub` claim via `User.FindFirstValue(ClaimTypes.NameIdentifier)`.

Domain model (`backend/src/OtoParcam.Domain/Entities`): `Product`, `Category`, `VehicleBrand`, `VehicleModel`, `ProductImage`, `ProductCompatibility` (product↔vehicle model many-to-many), `ApplicationUser` (extends `IdentityUser<Guid>`), `Favorite`, `PurchaseRequest`, `PurchaseRequestItem`, `AcquisitionBatch`. Key relationships:
- A `Product` belongs to one `Category` and has a source `VehicleModel`, plus many compatible `VehicleModel`s via `ProductCompatibility`, and optionally one `AcquisitionBatch` (many Products may share a batch).
- A `VehicleModel` belongs to one `VehicleBrand`.
- A `PurchaseRequest` belongs to one `ApplicationUser` and holds many `PurchaseRequestItem`s, each snapshotting both `OriginalPrice` and `NegotiatedPrice` for a `Product` — the `Product.Price` itself is never mutated during negotiation (BR-31/BR-33/BR-34).

Purchase request status flow (`PurchaseRequestStatus` enum) drives the core order workflow and is never set directly by clients — only via the dedicated action endpoints: `Pending → WaitingForCustomerConfirmation` (admin negotiation) `→ Approved | Rejected` (customer confirm/reject — the customer, not the admin, triggers the terminal transition; BR-26/BR-32), plus `Cancelled` (customer-only, only while `Pending`). Stock/status changes on the `Product` happen only when a request reaches `Approved`.

## API design

`docs/06-Api-Design-Specification.md` is the authoritative REST contract (base path `/api/v1`, JSON, JWT bearer auth) — implement controllers to match its endpoint list, status codes, and access rules (Public / Customer / Administrator) rather than inventing new routes. Notable conventions from that spec:
- `DELETE /products/{id}` is non-destructive — it sets status to `Hidden`, it does not delete the row.
- Purchase request status transitions are exposed as dedicated `PATCH .../cancel|confirm|reject` actions and an admin `PATCH .../negotiation` action — there is no generic "update status" endpoint.
- Product listing (`GET /products`) is paginated at a fixed page size of 20 and supports `categoryId`, `vehicleBrandId`, `vehicleModelId`, `keyword`, `color`, `page`, `sortBy` (`priceAsc`/`priceDesc`, with unpriced products sorted last).

`docs/` contains the full spec set and should be treated as living requirements documentation, kept consistent with the code:
- `01-Project-Vision.md`, `02-Business-Requirements.md` (numbered `BR-*` business rules), `03-Software-Requirements-Specification.md`, `04-Use-Case-Specification.md`, `05-Database-Design.md`, `06-Api-Design-Specification.md`, `07-ERdiagram.drawio`.
- `docs/Notes/EntityProcess.md` is a working-notes log of per-entity design decisions and progress — check it for context/rationale not repeated in the numbered specs. It anticipated `Product.Side`/`Position` as nullable fields before they were implemented (2026-08-05); both now exist as nullable `ProductSide`/`ProductPosition` enums on `Product`, left null for categories where the attribute doesn't apply (e.g. Hood has neither, Door has both) — this is an admin judgment call per product, not schema-enforced per category.
- `docs/Notes/ DECISION_LOG.md` is a lightweight ADR log (DECISION-001 through DECISION-008) — read it for the *why* behind schema choices that might otherwise look like gaps (no stock quantity, nullable price, no condition column, manual compatibility selection, source-vehicle semantics, SQL Server over PostgreSQL, lump-sum acquisition batches, `SoldPrice` as a real column).

Known gaps between docs and current code/decisions, worth checking before trusting either as ground truth:
- `05-Database-Design.md` §2 says the project follows a **Database-First** approach, but the actual implementation is **Code-First** (entities + Fluent API configs → EF migrations). Treat Code-First as the real approach until that line is corrected.
- `07-ERdiagram.drawio` is not an editable diagram — it's a single embedded raster image (~319KB) pasted onto a draw.io canvas, with no real shape/text nodes. Text search/replace against it will silently find nothing; regenerating it means building a new diagram from scratch, not editing the existing file.
- BR-02/BR-60 ("every Product must have 1–10 images") and BR-07 ("compatibility must be specified before a product becomes available") are **not enforced as blocking gates**. `POST /products` creates a product with `Status = Available` by default (per BR-05) even with zero images/compatibility records, since Image and Compatibility management live behind separate endpoints per the API spec's section split (§9/§10) rather than the create-product payload. There is also no "draft"/"incomplete" status in `ProductStatus` to gate on. Treat this as a real product-workflow decision to revisit, not an oversight to silently patch — check with the user before adding blocking validation here. (`POST /products` can also take an optional `Status` — `Available` or `Hidden` only, `Sold` rejected — for inventory-only parts never meant for public sale; `PUT` still has no `Status` field, editing status stays on the dedicated hide/restore endpoints. BR-77, added 2026-08-11.)
- `GET /products/{id}` (detail view) does **not** filter out `Hidden`/`Sold` products the way `GET /products` (the list endpoint) does — this was a deliberate reading of the API spec's "shall not appear in public product listings" wording as applying to the collection endpoint specifically, so an admin can still fetch a hidden product by ID to edit it. `GET /products` itself now also exposes every status to Administrator callers (via an optional `status` query param, ignored for public/Customer callers who still only ever see `Available`), and `PATCH /products/{id}/restore` moves a `Hidden` product back to `Available` (Administrator only, rejected with a conflict if the product isn't currently `Hidden` — `Sold` is terminal and not restorable this way).
- `ProductDto.Title` is generated dynamically in `ProductService.BuildTitle` (`"{Brand} {Model} {Variant} ({StartYear}-{EndYear})"`) since the docs only say a title is "generated dynamically at runtime" from the source vehicle without specifying a format — this exact format is an implementation choice, not a documented spec.
- `Product.AcquisitionCost`/`AcquisitionSource` and the `/admin/reports/statistics` PDF report implement `03-Software-Requirements-Specification.md` §6's "Sales analytics"/"Advanced reporting" Future Enhancements (and partially "Supplier management") ahead of schedule, brought into scope at the user's explicit request on 2026-08-10 rather than left deferred — not an oversight if these show up as "future" in the SRS elsewhere, that line is simply stale now. `AcquisitionCost`/`AcquisitionSource` are stripped to `null` for every non-Administrator caller in `ProductService.GetProductsAsync`/`GetProductByIdAsync` (both take an `isAdmin` bool threaded from `User.IsInRole` in `ProductsController`) — never expose them in a new endpoint/DTO without the same gating, since leaking cost basis to customers is a real business-confidentiality concern, not just a data-shape nicety.
